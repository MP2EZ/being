## 2. Scope

**Processing activities covered by this DPIA:**

- Local-first capture, storage, and display of sensitive wellness data on a user's own device.
- Optional end-to-end encrypted backup to Supabase, gated on cloud-sync consent. It carries ONE app-setting field (an autosave preference) and no sensitive wellness data. DEBUG-625 removed a last-sync timestamp that was written on every PHQ-9/GAD-7 save: because the change-detection hash covers exactly this payload, that field made backup timing — and the operational telemetry below — track screening activity. The encryption key stays on the user's device; Supabase has no decryption capability.
- Subscription billing metadata processed via Stripe. Stripe receives payment instruments and transaction state; Stripe does not receive any wellness content.
- Subscription entitlement verification via **Apple's App Store Server API**. Being sends one stored transaction identifier (`subscriptions.original_transaction_id`, Apple's own identifier) and receives Apple-signed transaction and renewal payloads. No wellness content is sent, and Apple learns nothing it did not originate. Two triggers: user-initiated verification (`verify-apple-receipt`) and, since DEBUG-474, a nightly server-side re-verification (`grace-period-automation`) that runs with no user present. Legal basis: contract performance (§4). Apple is already a disclosed recipient — `privacy-policy.md` §5.1.
- Product analytics (PostHog) — feature-engagement events (corrected 2.60: PostHog has never received severity buckets, and since DEBUG-821 receives no crisis-access, screening, guidance or screening-history event), transmitted only when the user has granted analytics consent (PostHog is not initialized without it; universal opt-out suppresses transmission). PostHog receives no raw screening scores, no Q9 value and no journal content. It does receive a random per-installation identifier, device and app details (model, OS and app version, screen size, language, time zone) and a city/country location derived by the project's GeoIP transformation (corrected DEBUG-788; see 2.42). EU data residency (Frankfurt).
- Crisis-detection telemetry (Supabase `analytics_events`) — a `crisis_detected` event recorded to Being's own first-party table when a PHQ-9 total ≥20, a non-zero PHQ-9 Q9, or a GAD-7 total ≥15 is detected. Recorded **regardless of analytics consent** under GDPR Art. 6(1)(d)/9(2)(c) vital interests (see §4 and the standalone `lia-crisis-telemetry.md`). Payload: `trigger_type` (category — `phq9_suicidal_ideation` / `phq9_severe_score` / `phq9_moderate_severe_score` / `gad7_severe_score`), `severity_bucket`, `intervention_surfaced`, `assessment_type`, and — since DEBUG-541 — `detected_on`, the UTC calendar day the threshold was crossed (`'YYYY-MM-DD'`, clamped server-side to no later than the ingest date). No raw score, no Q9 value, no time of day, no device identifier. **Identifier description corrected DEBUG-409:** each row also carries `user_id`, the persistent INFRA-260 `auth.uid()` anonymous-session principal (`analytics_events.user_id` is `NOT NULL REFERENCES users(id)`), and `session_id` rotates per process rather than per calendar day (minted once in the `SupabaseService` constructor, UTC-derived date component). Both are pseudonymous, first-party and RLS-isolated, never linked to an email, profile or sign-in identity, and shared with no third party — but they are not absent, and earlier versions of this document described them as such. See `lia-crisis-telemetry.md` §2. **Identifiability corrected DEBUG-850:** `user_id` is the Supabase Auth principal, and `auth.sessions.ip` / `user_agent` hold the latest connection's IP address and user agent, so the row is linkable by the controller to a network address in one join, and `created_at` is an unrounded server arrival time. "No time of day" and "no device identifier" describe the transmitted payload only. See §6.1 Scenario 1. **De-linked INFRA-861 (v2.67):** crisis rows now carry no `user_id` and no `session_id`, `created_at` is truncated to the UTC day, and `properties` is rebuilt server-side from the five allowlisted keys; a trigger and CHECK constraints enforce this for every role (`supabase/migrations/20261024000000_infra861_crisis_delink.sql`). The app sends the event without a user token and no longer creates the random account ID for it. Pre-change crisis rows were deleted. Server retention is 90 days from receipt. The identifier and DEBUG-850 descriptions above apply to rows that no longer exist. The row is not anonymous: see `lia-crisis-telemetry.md` §2 for the residual linkage.
- Error and crash telemetry via Sentry — payload scrubbing in place per §7. Sentry also receives release-health session data (session start/end, duration, crash status); sessions and native crash, app-hang and watchdog-termination events carry a per-install identifier, and native crash events also carry a vendor-derived device identifier and a city/country Sentry derives from the connection (none linked to identity or wellness data; v2.43); see §9 v1.7 for the retrospective finding. Since v2.39 (DEBUG-776) all of it is gated on the user's *Crash Reports* consent and suppressed by Universal Opt-Out. A bug report the user chooses to send is sent whatever the *Crash Reports* setting: with it off, through a feedback-only client with no crash handler, sessions, breadcrumbs or identifier; with it on, through the consented client, carrying device and app context; `scrubFeedbackEvent` deletes `user` and `contexts.app.device_app_hash`, so neither the per-install nor the vendor-derived device identifier is sent (v2.44).
- Crisis-monitoring operational egress — the `crisis-detection-alerting` edge function emails the founder on a breach via **Resend** (aggregate, non-personal alert payload; see §9 v1.4) and fires a PII-free liveness heartbeat to **healthchecks.io** as an external dead-man's-switch (INFRA-264; an opaque HTTP ping carrying no user data, no wellness data, and no identifier — see §9 v1.6). Neither receives sensitive wellness data.

**Out of scope.** Being does not engage in advertising, data sale, third-party sharing for non-service purposes, profiling for automated decisions, or training of generative models. See `docs/legal/privacy-policy.md` §5 for the public confirmation.

**Architecture summary.** Local-first by design. The user's device is the primary system of record; optional cloud backup contains only an opaque encrypted blob of app settings, with no sensitive wellness data. The full technical specification is in `docs/security/security-architecture.md`.

## 3. Data Categories and Sensitivity Classification

The following categories are classified as **sensitive personal information** under one or more of the triggering statutes. Mental and physical health condition data is enumerated as "sensitive data" in each statute's definitional section (see §11).

| Category | Examples | Classified sensitive under |
|---|---|---|
| Wellness screening responses — depression module | PHQ-9 item responses, total score, Q9 self-harm indicator | TDPSA, CPA, VCDPA, CTDPA |
| Wellness screening responses — anxiety module | GAD-7 item responses, total score | TDPSA, CPA, VCDPA, CTDPA |
| Mood check-in records | Numeric mood rating, optional context tag | TDPSA, CPA, VCDPA, CTDPA |
| Reflective writing | Journal entries from Stoic Mindfulness practices | TDPSA, CPA, VCDPA, CTDPA |
| Consent records for sensitive-data processing | Acknowledgment timestamps for explicit consent under GDPR Art. 9(2)(a) where applicable, and state-law sensitive-data consent | Derivative — sensitive because the consent record itself confirms a user's participation in mental wellness self-screening |
| Subscription status and transaction history | Active plan, billing events, entitlement status for paid features (crisis access is free on every plan, and no crisis path reads subscription state) | Derivative — sensitive because correlation confirms ongoing engagement with mental wellness self-monitoring services |

Where this DPIA refers to "sensitive wellness data" without qualification, all six categories are intended.

That state-law sensitive-data consent is the operative basis for each purpose involving categories enumerated in §3; tracking is described in the consent-records entry of §3. The "GDPR Art. 6 equivalent" column below maps each purpose to the corresponding GDPR lawful basis for cross-jurisdictional clarity — it is the equivalent, not a substitute for state-law consent.

## 5. Necessity and Proportionality

For each category in §3, Being collects the minimum needed for the stated purpose.

- **PHQ-9 (nine items)** is the standard short-form depression screener. A shorter instrument (PHQ-2, PHQ-4) was considered and rejected: it omits Q9 (self-harm indicator), which is the technical basis of Being's crisis-resource routing. PHQ-9 is the minimum that preserves the crisis-detection capability.
- **GAD-7 (seven items)** is the standard short-form anxiety screener. The GAD-2 sub-score lacks the granularity needed for the trend visualizations that motivate sustained self-monitoring. GAD-7 is the minimum that preserves the user-facing insight.
- **Mood check-ins** capture a single numeric rating and an optional context tag. This is the minimum signal needed to plot a mood trend.
- **Journal entries** are user-authored reflective writing. The user controls content and length. Being reads the text of an entry on the device in two ways, and in no other. (1) The keyword crisis scan (FEAT-283) matches a fixed phrase list against the text at capture and at save, so that support resources are offered; its result is a categorical event (a scan fired, a severity bucket, whether support was shown), never the text. (2) The lexical search index (FEAT-530) lists the distinct words of each entry (lowercased, accents removed) beside the entry's ID so that the user can find an entry by its words; it stores no counts, frequencies, positions or classifications, is encrypted under the same key as the entry and is deleted with it. Neither is analysis of what the writing means: Being makes no classification, sentiment, topic or machine-learning inference from an entry, and no third party receives its text or its words.
- **Crisis-resource access** collects nothing of its own. Being refers users to external crisis services (the 988 Suicide & Crisis Lifeline, the Crisis Text Line and 911) and does not provide safety planning. No content or contact details are collected for this purpose; the only category it uses is the PHQ-9 Q9 response enumerated above. This describes the scope of the app and is not a clinical judgement about safety planning.
- **Consent records** are collected because GDPR Art. 9(2)(a) requires them where it applies, and because state-law sensitive-data consent is a best-practice control. The record contains a timestamp and the acknowledged scope only — no derivative information.
- **Subscription metadata** is the minimum needed to enforce paid-tier entitlements; raw payment instruments are processed by Stripe, not by Being.

Local-first storage is the primary proportionality control: sensitive wellness data is stored on the user's device and is not part of cloud backup. When the user opts in, backup transmits only an opaque encrypted blob of ONE app-setting field (an autosave preference).

## 6. Risk Assessment

Scored on a qualitative 3×3 likelihood × impact matrix (Low / Med / High). "Pre-mitigation" assumes only baseline operating-system controls (no Being-specific protections). "Post-mitigation" reflects the controls inventoried in §7.

| # | Threat scenario | Pre-mitigation (Likelihood × Impact) | Post-mitigation (Likelihood × Impact) | Residual |
|---|---|---|---|---|
| 1 | Re-identification of an individual from analytics and crisis-detection records | Med × High | Low × High | **Medium** |
| 2(i) | Unauthorized access to sensitive wellness data via a lost or stolen **locked** device | High × High | Low × High | **Low** (likelihood) — see rationale |
| 2(ii) | Access to sensitive wellness data by someone holding an **unlocked or shared** device | Med × High | Med × High | **Medium** — no Being control; accepted in §8 |
| 3 | Compromise of optional cloud backup at the Supabase storage layer | Low × High | Low × Low | **Low** |
| 4 | Leakage of sensitive wellness data through error or crash telemetry (Sentry) | Med × Med | Low × Low | **Low** |

### 6.1 Rationale per scenario

**Scenario 1 — Re-identification from analytics and crisis-detection records.** After the INFRA-214 consolidation the analytics pipeline has two sinks, neither of which receives raw screening scores, Q9 values or journal content. **PostHog** (product analytics, consent-gated) carries feature-engagement events under EU data residency (Frankfurt) (corrected 2.60: not severity buckets); **corrected DEBUG-788:** each PostHog event also carries a device-persistent random identifier, device and app details, language and time zone, and a city/country location added by the project's GeoIP transformation, so PostHog does hold quasi-identifiers. Its re-identification control is that the identifier is never `identify()`'d to `auth.uid()` (no person profiles exist) and the events carry no wellness content — not the absence of quasi-identifiers. **Supabase `analytics_events`** (crisis-detection telemetry, vital-interests basis) carries only `trigger_type` (category), `severity_bucket`, `intervention_surfaced`, `assessment_type`, and (since DEBUG-541) `detected_on` — a UTC calendar day, never a clock time; the gap between it and `created_at` discloses at day resolution that the device was offline across that interval, which is accepted on the record as a residual in `lia-crisis-telemetry.md` §3 and does not introduce a quasi-identifier; **Identifier description corrected (DEBUG-409).** This scenario previously stated that `session_id` "does not persist across calendar days" and implied no persistent identifier accompanied the row. Accurately: each row carries `user_id` — the persistent `auth.uid()` anonymous-session principal minted by INFRA-260 `signInAnonymously` — and a `session_id` that rotates per process rather than per calendar day (a DB CHECK constraint enforces the `session_YYYY-MM-DD_…` format, but the value is minted once per `SupabaseService` construction and its date component is UTC-derived). RLS isolates rows by that identifier (`docs/security/supabase-rls-verification.md`, Analytics Events Table). **k-anonymity and differential privacy are NOT claimed** — the dead custom-API engine that notionally provided them was deleted in INFRA-214, and at pre-launch scale such thresholds are not operationally meaningful. **Identifiability corrected (DEBUG-850, 2026-10-23).** This scenario previously concluded that re-identification was controlled by severity-bucketing, a lack of quasi-identifiers, RLS isolation and the non-enumerability of `auth.uid()`, and that it remained not realistically achievable. The quasi-identifier premise was false for the controller. `auth.uid()` is the Supabase Auth principal, and `auth.sessions.ip` / `user_agent` hold the latest connection's IP address and a coarse device string (app build number plus OS kernel version, verified 2026-10-23), rewritten on every refresh (144 of 144 hosted sessions carried an IP on 2026-10-22, MAINT-847). So `analytics_events.user_id` → `auth.sessions` is one join from a crisis-detection category to a network address, and `created_at` is an unrounded arrival time. The linked field set includes the `phq9_suicidal_ideation` category, so post-mitigation **impact is High**. Likelihood stays **Low** on controls that are true today: no Being code reads `auth.sessions.ip` or `user_agent`; Being holds no name, email or contact dataset to join an IP address to; turning an IP address into a person needs ISP records or legal process; the auth schema is not exposed through the API; RLS is enforced at runtime; and access is founder-only. A Supabase compromise exposing `analytics_events` and `auth.sessions` together would yield crisis status identifiable by IP address, which is identifiable health information under 16 CFR Part 318 (backstop, §8). **Post-mitigation residual: Medium** until INFRA-851 (minimise the session IP address and user agent) and INFRA-848 (bound orphaned identities) land. Accepted in §8. **Updated v2.67 (INFRA-861):** the crisis-row half of this scenario no longer rests on the `auth.sessions` join. Crisis rows carry no `user_id` or `session_id`, `created_at` is a UTC day, the table enforces both for every role (control 24), and every pre-change row was deleted. What remains for crisis rows is the residual linkage in `lia-crisis-telemetry.md` §2: 1-day request logs holding the sending IP address, a small known cohort, same-day co-occurrence with identified writes, and the offline gap. The rating is held at **Medium** rather than re-rated: the PostHog half is unchanged, and whether the crisis rows meet the state-law deidentified-data definitions is a counsel question (§8). Re-rate when counsel rules.

**Scenario 2 — Unauthorized device access.** Split at v2.16 (DEBUG-624), because the two halves have different controls. **(i) Lost or stolen locked device.** This is the highest-impact half, because device loss is common. Sensitive wellness data is encrypted at rest with AES-256-GCM, and the master key is held in `expo-secure-store` (the iOS Keychain with its default `WHEN_UNLOCKED` accessibility; the Android Keystore). See `docs/security/security-architecture.md` §1 (Encryption Methods for Local Storage) and §3 (Access to Sensitive Views). An attacker with a locked device must defeat both the device lock and the OS keystore, so likelihood is Low. Impact, were they to succeed, remains High because the content is sensitive. The user remains the last line of defense by setting and protecting their device passcode/biometric. **(ii) Unlocked or shared device.** Being has no in-app authentication gate and no auto-lock; §7 controls 3 and 4 are withdrawn. Anyone who can unlock the device, or who is handed it unlocked, can open Being and read everything in it. No Being control reduces this: the device lock and the user's own discretion about who uses their phone are the only protections. Likelihood is Medium, because sharing a phone with a partner, a family member or a child is ordinary. Impact is High. Residual: **Medium**, accepted by the founder in §8. An opt-in in-app lock would reduce it. Building one is a product decision not taken here. *Sub-note (v2.65, FEAT-807):* the export and account-deletion screens show the date of the most recent export. Someone holding the unlocked phone can therefore see that, and when, the user exported their data. This adds little to what the same person can already read in the app, and it falls under the same accepted residual.

**Scenario 3 — Cloud backup breach.** Optional cloud backups are stored as opaque encrypted blobs in the `encrypted_backups` table. The decryption key never leaves the user's device. Supabase Row-Level Security prevents cross-user access at the database layer (see `docs/security/supabase-rls-verification.md`, Encrypted Backups Table within RLS Policy Analysis). Even in the event of a full Supabase compromise, attacker yield is encrypted blobs without accompanying keys, and the blobs hold two app-setting fields and no wellness data. Residual: Low.

**Scenario 4 — Sentry telemetry leakage.** React Native error boundaries can capture local variable state into error payloads. Production mitigations: a `beforeSend` hook in `app/src/core/services/logging/ExternalErrorReporter.ts` (`beforeSendHook`, line 541) sanitizes every event before transmission — a crisis-content scan over named content-bearing surfaces (`collectContentText`, line 626) that drops a matching event **wholesale**, then an allowlist rebuild (`applyAllowlist`, line 695), then a dedicated wellness-data scrubbing path (`scrubSensitiveData`, line 770); sensitive-data variables are never passed into log lines or exception messages by convention. Stack frames are exempt from the content scan and coarsened instead — see controls 10a/10b in §7 for the ruling and its prospective status. Defense-in-depth for the development environment: the dev-environment Sentry DSN is empty (configured in `app/src/core/config/env.ts`), so a developer's local debugging cannot transmit at all — this is a developer-side safeguard, not a production control. Residual: Low. This scenario warrants explicit attention at every annual review since the React Native error-boundary surface area can grow with new features.

Retrospective correction (INFRA-295, v1.7): a naming mismatch (`autoSessionTracking` vs. the SDK's actual `enableAutoSessionTracking`) meant release-health session envelopes — which carry no wellness content but, absent an explicit `Sentry.setUser` call, do carry a per-install identifier via the native layer's `did` fallback — were most likely transmitted from every production build to date. Note also that session envelopes are envelope *session items*, not events, so the `beforeSend` mitigation credited above does not apply to them; their privacy posture rests on the fixed session schema having no field for user content. See §9 v1.7 for the finding and remediation.

## 8. Residual Risk Acceptance

After applying the controls inventoried in §7, residual **likelihood** is Low for scenarios 1, 2(i), 3 and 4, and **Medium for scenario 2(ii)**. Residual **impact** is High for scenario 1 (re-rated by DEBUG-850), Low for scenarios 3 and 4, and High for both halves of scenario 2. For 2(i), the layered controls reduce likelihood to Low, but defeating the device-unlock plus OS-keystore chain would expose sensitive wellness content. For 2(ii), no Being control applies (see the accepted residual below). The per-scenario rationale is recorded in §6.1.

**Acceptance.** Palouse Labs LLC accepts the residual risk for the processing described in §2 on the basis that:

1. Except for scenario 2(ii), no single mitigation in §7 is the sole defense for any scenario in §6 — controls are layered. Scenario 2(ii) has no Being control at all, and its acceptance is recorded separately below.
2. Local-first architecture limits attacker yield in cloud scenarios to encrypted blobs.
3. The user retains direct control over device access and over whether to enable cloud backup.
4. No technical control can eliminate device-loss risk; for scenario 2(i), the user's enrollment of a device passcode/biometric is the irreducible final layer.

**Accepted residual — unlocked or shared device, scenario 2(ii) (v2.16, DEBUG-624; founder decision 2026-09-14).** Being has no in-app authentication gate or auto-lock, so someone holding an unlocked or shared device can read all sensitive wellness data in the app. This is the first residual in this assessment above Low. Palouse Labs LLC accepts it on the following basis:

1. **The exposure is local.** It is a disclosure to people who already have access to the user's device, not a remote or bulk exposure. No sensitive wellness data leaves the device, and no server copy exists.
2. **No surface promises otherwise.** The privacy policy, the consent screens and in-app copy make no claim of in-app biometric or passcode protection, so users are not led to rely on a control that does not exist. `security-architecture.md` §3 and §4 now forbid such copy.
3. **No triggering statute mandates app-level authentication.** Each requires reasonable safeguards proportionate to the data. Encryption at rest and OS-protected key storage (§7 controls 1–2) provide those safeguards against the lost-device half of this scenario.
4. **The reduction is known.** An opt-in in-app lock would reduce this residual. Building one is a product decision not taken here, and any such lock must never put an authentication prompt between a user and 988.

**Accepted residual — `critical_log_*` records on pre-fix installs (v1.9, DEBUG-355).** Control 17 stops the write, but it cannot reach records already on a device. Those records are **irreducible**, not merely unremediated: they live in SecureStore under `critical_log_<epoch>` keys, SecureStore exposes no enumerate API, and no index of what was written was ever persisted. A remediation sweeper is therefore not a "not yet built" item — it is not constructible without first shipping a build that records an index of the very keys we want gone, which would mean writing *more* of this data to delete some of it. Palouse Labs accepts this residual on the following basis:

1. **Bounded and shrinking.** No new records are created from this version onward. The existing set is fixed and decays with app reinstalls and device turnover.
2. **Confined and OS-protected.** The records never left the device — no transmission, no sub-processor, no server copy. They sit in the iOS Keychain / Android Keystore, i.e. behind the same OS-protected store credited as control 2, so their exposure profile is scenario 2. For a locked device, that is 2(i), assessed at Low likelihood. On an unlocked or shared device (2(ii)) no code path reads these records, so the app shows nothing of them to the person holding it.
3. **Content is derived and bounded, not raw.** Entries are sanitized log records: message, category, level, timestamp, and an anonymous session hash. `ProductionLogger.crisis()` accepts only `detectionTime` / `interventionType` / `severity` by construction and no scores, responses, Q9 values, or identifiers.
4. **The erasure right is honoured going forward, and the master-key deletion limits reach.** A user exercising deletion today gets every current-generation record removed. Pre-fix residue is not re-created and holds no key material.
5. **No notification obligation arises.** Consistent with the v1.8 assessment of the DEBUG-305 records: local-only, never transmitted, no evidence of unauthorized access, so no 16 CFR Part 318 trigger. This is a self-identified defect closed by us, not an incident.

Recorded here rather than left silent because §3 and `lia-crisis-telemetry.md` §4 safeguard 6 both previously asserted that no durable local crisis record persists. That assertion was false while these writes existed; it becomes true prospectively with control 17, and this residual is the honest qualification on the retrospective half.

**Accepted residuals — account erasure edges (v2.38, DEBUG-775).** Each is local, holds no wellness content, and is narrower than a window the user can observe:

1. **Killed between the server delete and the erasure-pending marker write.** The server account is gone and the local wipe never ran, and nothing on the device records that it should. The next launch therefore behaves as a signed-in install with the deleted account's local data, until the user deletes again (the retry converges through the server, DEBUG-704). Accepted at b-batch 2026-10-09: the window is one AsyncStorage write wide, and closing it would require writing the marker before the server confirms, which would retire a launch for an erasure that may never happen.
2. **A backup already in flight.** `createBackup` checks `cloud_sync` consent before its upload and writes `@being/cloud_backup/last_backup` (time, hash, size) after it. An upload that passed its check before the wipe can land that key afterwards. No wellness data; it is swept by the next erasure and overwritten by the next consented backup.
3. **An orphaned rotated master key on a Keychain fault.** `mental_health_master_key_v2` is deleted best-effort, so a fault leaves 32 random bytes that no code reads and nothing is encrypted under. A strict delete would instead leave the erasure marker set and route every launch to LegalGate while the fault persisted (crisis + compliance ruling).
4. **A warm deletion that starts during a retention pass.** The retention fence covers a pending or in-flight erasure at the start of the run; a deletion the user confirms in the sub-second window while a launch's retention pass is mid-write is not re-checked before each write-back. Tracked, not closed.

**Accepted residual — identifier linkage through Supabase Auth session records, scenario 1 (v2.55, DEBUG-850; founder decision at batch approval 2026-10-23).** Scenario 1 is now Medium (§6). The residuals below are accepted as an interim position, not as the end state:

2. **Small cohort.** The founder is the only user today, and the next users are a small, known group of testers. A day-level row can be attributed by inference. The views apply no k-anonymity suppression, by design.
3. **Co-timing and ordering.** Same-day co-occurrence with identified operational rows sent by the same foreground handler, and sub-day ordering against adjacent writes through heap order and transaction ids. The row id must never become time-ordered.
4. **No erasure on request.** Users cannot have their crisis rows deleted, because no one can tell which rows are whose. Bounded by the 90-day retention, and by deleting every pre-change row rather than de-linking it, so no row collected under the old "deletion deletes the event" promise survives.

## 10. GDPR Article 35 Scope Note

A full GDPR Article 35 DPIA has been intentionally scoped out of this document. Being currently has minimal EU/EEA user presence. GDPR Art. 35 has no numeric threshold for when a DPIA is required — the test is qualitative ("high risk to the rights and freedoms of natural persons," with the WP29/EDPB nine-criterion guidance). Being has adopted the following self-imposed conservative triggers, which are stricter than the GDPR qualitative test alone: promote this DPIA into a GDPR-conformant artifact (a) before EU/EEA user count exceeds 500, or (b) before any feature constituting "large-scale processing of special category data" under Art. 9 is enabled — whichever occurs first. The above is itself a material-change trigger per §1.

## 11. Statutory Citations Appendix

The following statutes require a documented data protection assessment for processing of sensitive personal information. Mental and physical health condition data is enumerated as sensitive in each statute's definitional section.

### Texas Data Privacy and Security Act (TDPSA)

- **Citation:** Tex. Bus. & Com. Code §541.105(a).
- **Effective:** July 1, 2024.
- **Sensitive data definition (Tex. Bus. & Com. Code §541.001):** Personal data revealing physical or mental health diagnosis is enumerated as sensitive.
- **Assessment requirement (§541.105(a)):** A controller "shall conduct and document a data protection assessment" for processing of sensitive data.

### Colorado Privacy Act (CPA)

- **Citation:** C.R.S. §6-1-1309.
- **Effective:** July 1, 2023.
- **Sensitive data definition (C.R.S. §6-1-1303):** Personal data revealing mental or physical health condition is enumerated as sensitive.
- **Assessment requirement (§6-1-1309):** Controllers must conduct a data protection assessment of processing activities that involve sensitive data.

### Virginia Consumer Data Protection Act (VCDPA)

- **Citation:** Va. Code §59.1-580.
- **Effective:** January 1, 2023.
- **Sensitive data definition (Va. Code §59.1-575):** Personal data revealing mental or physical health diagnosis is enumerated as sensitive.
- **Assessment requirement (§59.1-580):** Controllers shall conduct and document a data protection assessment for processing of sensitive data.

### Connecticut Data Privacy Act (CTDPA)

- **Citation:** Conn. Pub. Act 22-15 §6.
- **Effective:** July 1, 2023.
- **Sensitive data definition (§1):** Personal data revealing mental or physical health condition or diagnosis is enumerated as sensitive.
- **Assessment requirement (§6):** Controllers must conduct and document a data protection assessment of processing of sensitive data. The Connecticut requirement is substantively parallel to the Colorado requirement.

### Federal Trade Commission Act, Section 5

Not an assessment-requiring statute. Listed for context: misrepresentation in this DPIA, in Being's privacy policy, or in any user-facing surface would constitute a "deceptive practice" under 15 U.S.C. §45.

### Federal Trade Commission Health Breach Notification Rule

- **Citation:** 16 CFR Part 318.
- Applies to non-HIPAA entities (including Being) that handle "PHR identifiable health information." Sets a 60-day notification window. Operationalized in `docs/legal/privacy-policy.md` §4.4. Referenced here as the breach-time backstop to the residual-risk acceptance in §8.
